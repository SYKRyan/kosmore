# Kosmora integration evidence

Inspected 2026-11-04. This is an observed private web-client contract, not a stability guarantee or an official public API. Never log authentication headers or commit account inventories. Fixtures in `tests/fixtures` are synthetic.

## Transport

The delivered request wrapper prefixes paths with `/api`, sends `credentials: same-origin`, and accepts JSON. Mutations additionally send `Content-Type: application/json` and `x-kosmora: 1`. KosMore implements explicit album add and single-subject removal actions. It never retries a mutation automatically or invokes the native membership-toggle button.

| Request                                                         | Response used                                                                                                   | Evidence                                                                                                                  |
| --------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| `GET /api/me`                                                   | `handle`, nullable `currentOpening.id`                                                                          | Signed-in read; public request/session wrapper                                                                            |
| `GET /api/collection/{subjectId}`                               | `subjectId`, `name`, `rarity`, `interest.count`, `popularity.medianDailyViews`, `popularity.source`, `copies[]` | Signed-in read and card-detail client                                                                                     |
| `GET /api/cards/{subjectId}/prices?finish=plain\|veil\|fullart` | `{prices:{count,days,low,median,high,sales:[{auctionId,price,soldAt}]}}`                                        | Plain response read live; finish enumeration and schema checked in delivered CardSales module                             |
| `GET /api/albums`                                               | `{albums:[{id,name,items,...}]}`                                                                                | Native album list and picker code                                                                                         |
| `GET /api/albums?contains={subjectId}`                          | Album list plus `contains`, `containsCount`                                                                     | Signed-in read and picker code                                                                                            |
| `GET /api/openings/{openingId}`                                 | `id`, `state`, nullable `cards[]` with `slot`, `subjectId`, `instanceId`, `rarity`, `veil`, `card.fullArt`      | Read endpoint inspected in preparing state; populated schema and ordering established from delivered opening/recap client |
| `POST /api/albums/{albumId}/items`                              | Body `{subjectIds:[subjectId],copyId}`; response includes `added`                                               | Delivered native AlbumPicker add branch only; never exercised live                                                        |
| `DELETE /api/albums/{albumId}/items/{subjectId}`                | JSON body `{}`; membership absence is confirmed through the album list                                        | Delivered native AlbumPicker single-subject remove branch and JSON transport; never exercised live                        |

Market amounts are integer strings in millionths of a Kosmo (`100000000` displays as `100`). Count/price summaries cover the response window; transactions can be a smaller sample. A response window other than 30 days is rejected until the integration is updated. Wikipedia medians may be fractional and are not counts of interested players.

## Important semantics

- Album containment is queried at the subject level, even when a particular owned copy is selected for addition. If the album already contains the subject, KosMore does not replace its selected copy or invoke an add/delete toggle.
- The native picker has separate POST-add and DELETE-remove branches. KosMore uses a separate red trash action for removal and checks account identity and containment again immediately before either action. The album name itself never toggles membership.
- For addition, a copy must still appear in the current signed-in account's `/collection/{subjectId}` response immediately before the write. A copy ID in a market, social, or card URL does not prove ownership. Removal targets the verified subject-level membership and does not depend on which owned copy is selected.
- The native market finish selector uses `plain`, `veil`, and `fullart`. Copy flags preserve both `veil` and `fullArt`; visual recognition uses `.kc-veil`, `.kc-fa`, and reveal classes. Full art takes precedence in the native market finish classification.
- No dedicated fresh Wikipedia request is needed: the card detail already carries the recorded median and source.
- The delivered card-detail client links owned copies to `/market/sell?subject={subjectId}&instance={copyId}`. The gavel uses this navigation only after fresh account/ownership checks and requires an available copy. It does not submit a market mutation.

## Pack identity and DOM mapping

The recap client flattens openings in the URL's order, sorts each opening's renderable cards by `slot`, and uses opening ID plus slot as the entry identity. The reveal client sorts standard before shiny before full-art, then ascending rarity and slot. KosMore reproduces this ordering only to obtain a candidate, then independently validates its subject and finish against the hovered DOM card and its exact instance against the owned-copy response.

Recap `.ko-grid > li` index, reveal `.ko-tray > li.on` count, and `.ko-viewer-count` provide the corresponding visible entry. Ambiguous or changed mappings fall back to an explicit owned-copy chooser. No private React props, fiber fields, hydration state, game local storage, or network interception hooks are used.

Verified selectors:

- Ordinary cards: `.kc-link`, `.kc-article`, `/card/{id}` links, `/media/cards/{id}/...` image URLs, `[data-testid=card-corner]`.
- Reveal: `.ko-card.ko-beat-shown .ko-face-front .kc-article`; ignore backs and hidden faces.
- Recap: `.ko-summary .ko-grid > li` and `.ko-grid-open` overlay.
- Native enlarged preview: `.ko-viewer-sheet`, `.ko-viewer-count`.
- Market activity: visible `a.mk-act-main` within `.mk-act` (Your turn and Your bids under way), and `a.md-lot-link` within `.md-lot` (Your cards on sale). The visible auction link anchors the popup for thumbnail, name, summary hover, and keyboard focus.

Delivered bundles consulted included `29r8uba_nhmde.js` (transport), `33yu_fe2y9x88.js` (card detail/owned copies), `18715hayuf10m.js` (price schema and finish selector), `0ihvnr133opgk.js` (album add/remove branches and viewer), and `12fwyn7dj2o02.js` (opening cards and ordering). Hash-based filenames are evidence labels, not runtime dependencies.

Market activity markup was rechecked against the public `/market` assets on 2026-11-04. In `2f2dt6_k7hg9v.js`, `e7` renders Your turn (`dash-turn`) and Your bids under way (`dash-bids`) using `eS`/`eB` compact auction rows. `eP` wraps each `CardFace` thumbnail in `.mk-act-art[aria-hidden="true"]`; this is decorative duplication of the row's visible name, rather than a hidden card. `eW`/`eH` render Your cards on sale (`dash-sale`) with `.md-lot-link` and `.md-lot-art`. The detector treats only the visible same-origin auction link as the activity root, reads the card subject from its visual face, and uses `.mk-act-name > b` or `.md-lot-name > b` for its title. Auction IDs and auction-link query parameters never supply a card/copy identity. Sibling bid/relist controls, fully hidden rows, and unidentified mystery backs do not resolve as cards. Synthetic fixtures reproduce these structures; no live auction write was performed.

## Private social reminders

The public social client (`3i4rvn2i63msn.js`, with shared `Page` in `0e4alq37o-niu.js`) renders the selected friend as `section.sb-page[data-testid="sb-friend-card"]` inside `.sb-side`. KosMore mounts its own Shadow DOM panel immediately after that section, below the entire friend panel. Identity comes from matching `.sb-links` collection (`/friends/{handle}/collection`) and profile (`/u/{handle}`) links. A present `/social?f={handle}` must agree; a desktop default selection may have no `f` parameter. Other social subpages do not mount an editor. This uses delivered DOM contracts without inspecting React internals.

Reminders use one `chrome.storage.local` key per normalized account/friend handle (`kosmore.friend.{account}.{friend}`), independently of tooltip settings. `/api/me` is read to verify the account; notes and selected family names are never sent to Kosmora. Handle renames create a separate reminder entry, as with account-specific album pins.

New family tokens come from `GET /api/atlas/families`, the complete catalog used by `useFamilyChoices(true)` in the delivered card filters (`2ace7u1ogy3d9.js`, module `357445`). The response is `{domains:[{id,name,families:[{id,name,parent?}]}]}`; the picker uses `id`, `name`, and the domain's name. A signed-in read in the built-in browser verified 24 domains and 1,461 families on 2026-11-04; an unsigned request returned 401. There is no pagination in this catalog response. The adapter validates and flattens it, caching reads with the existing account-scoped five-minute cache. The editor accepts selected or exactly matched catalog names, supports punctuation such as commas within a family name, and preserves previously saved names that no longer match. Names remain the local reminder representation for compatibility with the initial editor. A failed catalog read disables new selections and offers Retry without blocking notes or removing stored tokens. No family preference is changed on the game's server.

## Trade suggestions

`GET /api/collection/{subjectId}` also exposes `families:[{id,name,...}]`; the native card-detail client renders this list directly. A signed-in built-in-browser read confirmed this shape. KosMore retains all listed memberships for matching; it does not infer other families from domain names or parent metadata. Missing or malformed family data disables suggestions without disabling market insights or album actions.

The social client's `useSocial` reads `GET /api/friends` and uses `friends[]` with each friend's `handle`. A signed-in read confirmed the top-level `friends`, `incoming`, `outgoing`, `blocked`, `limits`, `requests`, and `looks` fields; that account had no friends. The populated friend-entry shape comes from the delivered social client and synthetic fixtures. Suggestions use only this current friend list, not pending requests or reminder records for former friends.

The Trade tab loads its friend list on first use, verifies the account, and reads only `kosmore.friend.{account}.{friend}` keys for those friends. Matching compares saved family names with the card's actual membership names, ignoring case and whitespace. It does not use substring matching, hidden game interest data, or another account's reminders. Matches rank by matching-family count, then handle. Changes to local reminders invalidate an open popup's suggestions. Refresh/Retry explicitly refreshes the friend list. No trade is submitted; links open `/social?f={handle}`.

## Card overlays and quest membership

Card-corner overlays use the same DOM adapter as hover detection and consider only rendered visual cards. Text-only links, hidden faces, and decorative backs are excluded. A single paced queue checks visible cards; signal snapshots are cached per account and card for 30 seconds, while underlying card and sale-history reads retain their five-minute caches. Late results are discarded when the card identity or settings change. All badges use isolated Shadow DOM and `pointer-events: none`; each indicator has a separate saved toggle and requires no hover.

The compact thumbnails within Market Activity's `.md-turn`, `.md-bids`, and `.md-sale` sections are excluded from overlay enumeration and from pending overlay results. They retain hover/focus detection, and the popup header still displays applicable indicators. Ordinary card overlays elsewhere remain controlled by their existing settings toggles.

The gavel badge requires a positive active-auction count for the exact subject across all finishes, using the same validated market search and 30-second count cache as the Active Auctions metric. A separate history badge requires a positive completed-sale count in at least one verified finish history within the 30-day response window. Either or both can appear; a past sale never creates an active-auction gavel. Their saved visibility settings are independent. Signal snapshots expire after 30 seconds, and card overlays retain the existing paced visible-card scan and five-minute invalidation cycle. An open popup gives its freshly loaded auction metric precedence over cached badge data, so Refresh can remove a gavel when auctions end. The friend badge uses the same current-friends and saved-family matching logic as Trade. Ordinary read failures suppress that signal; 401 pauses checks until session refresh and 429 respects the shared client cooldown.

`GET /api/quests` was verified through a signed-in built-in-browser read and the delivered quest hook (module `925729`, including `0qlrvpfh1jxkd.js` and `2ace7u1ogy3d9.js`). It returns `{quests:[{id,state,stars:[{subjectId,lit,...}],...}],following,max,cards}` without pagination. The inspected response and native quest catalog listed 30 quests of 15 stars each. KosMore extracts and deduplicates only validated subject IDs from every quest's stars. It does not store account progress, interpret `held` as membership, or require a quest to be followed. Lit stars remain members. The native `/quests/wanted` contract is intentionally narrower (followed quests still needing cards), so it is not used for this badge. No follow, drop, celebration, or quest mutation is called. Missing, locked, or unfamiliar catalogs produce no quest badge; sales and friend badges can still load. Synthetic fixtures preserve this response shape without account inventory or progress dumps.

## Private card notes and popup layout

Albums marked Already added display a small red trash icon at the right edge of their tile. It is an independently focusable button beside the disabled album-name button, positioned within the same visual tile; no buttons are nested. Only the trash action removes membership. The remove path was rechecked against public `/collection` assets on 2026-11-05 (`2fizp85-j0vrt.js`): a single selection sends `DELETE /albums/{albumId}/items/{subjectId}`, rather than a copy ID. The native transport (`29r8uba_nhmde.js`) serializes omitted write payloads as `{}` with JSON content type. KosMore follows that behavior; an empty body with JSON content type can produce HTTP 400. The client rechecks the account and album membership, shares the existing per-album/subject mutation lock, and confirms absence afterward. An absent membership is a no-op. A failed response is reconciled through a read without repeating DELETE. Unconfirmed or failed removals leave an error in the tooltip. Successful removal refreshes album buttons and keeps the tooltip open regardless of close-after-add preferences. Synthetic browser fixtures reject missing removal bodies and cover right alignment at 440/320 pixels, click isolation, keyboard activation, pending/failed removals, and removal without choosing a copy. No live album removal was performed.

`Settings.closeTooltipWhenAddedToAlbum` and its subsetting `Settings.applyCloseBehaviorToPinnedTooltips` both default to false for new and existing settings. The popup-settings toggle, Close Unpinned Tooltips When Added to Album, closes an unpinned tooltip after the client confirms a successful pinned-album addition. Its indented subsetting, Also Close Pinned Tooltips, is editable only while the main toggle is on and extends closing to pinned tooltips. Turning the main toggle off disables the behavior regardless of the saved subsetting, while preserving that preference for later. Closing uses the normal dismissal path to clear the saved pin state. Pending or failed additions leave the tooltip open. An addition completing after its popup was disposed never dismisses a newer popup.

`Active Auctions` is an enabled-by-default entry in the shared stat catalog. It counts open, unexpired auction listings for the exact subject across all finishes, independently of the completed-sale variant filters. Existing stat visibility and ordering are preserved, with the new metric appended.

The public market client (`2f2dt6_k7hg9v.js`, checked 2026-11-05) reads `GET /api/auctions?q={name}&sort=ending&offset={offset}` and consumes `{items,nextOffset,total}`. The native card detail's Find at Market link searches by card name. Signed-in read-only checks confirmed that a Fish search also matches other subjects, and a Triggerfish search returned an open exact-subject listing. Each returned item has `id`, `card.subjectId`, `state`, and `endsAt`. KosMore follows `nextOffset` to completion, deduplicates auction IDs, filters by exact subject ID and `state === "open"`, and excludes elapsed end times. Search totals and the signed-in account's own auction capacity are not used as this metric. An auction is counted once, including a lot; the metric does not count copies inside a lot.

Auction counts have a separate account-scoped 30-second cache; Refresh bypasses it. Requests use the shared rate-limit handling and a 15-second overall timeout. Malformed responses, failed later pages, non-advancing offsets, or searches exceeding 50 pages leave the metric unavailable instead of showing zero or a partial count. Hidden metrics do not start auction searches. Popup disposal aborts its request and ignores late results. Browser fixtures cover exact-ID counting, zero, failure/retry, finish-filter independence, and enabling the stat in an already-open popup. No market mutation is submitted.

The Notes tab uses one local key per normalized signed-in account and subject (`kosmore.cardNotes.{account}.{subjectId}`), independently of copies and finishes. Save rechecks the account before writing extension storage; no note text is sent to Kosmora. Dirty drafts survive tab changes. External storage changes refresh clean editors and preserve dirty drafts with a conflict message. Save/Cancel and storage errors are handled inside the editor.

Pinned albums appear first below the popup header, followed by the selected stat boxes, then the Market, Trade, and Notes tabs. Pinned albums use three columns. The selected tab panel and albums scroll independently, with an outer body scrollbar when the configured popup height requires it. Scrolling sections reserve a scrollbar gutter and inset their contents. Tab selection, loading, filtering, stat preference changes, and sales Show All/Show Less retain the configured popup dimensions within viewport limits. Recent sales labels the number displayed against the returned sample size (`Latest X of Y`); this denominator is not presented as total market activity.

`Settings.stats` stores ordered `{id,enabled}` entries from the shared stat catalog. Older settings default to the original six boxes. Parsing preserves existing order and disabled entries, removes unknown/duplicate IDs, and appends newly implemented stats. Popup and options use the same stat-box renderer, and live preference updates preserve open tab editors. Header badges use the exact same applicable-signal renderer and settings flags as card-corner overlays; they do not add new game requests beyond the existing cached signal provider. Reminder loading/error messages remain visible when needed, while the normal family-picker helper and private-storage subtitle are omitted.

Pinned visibility and each tab's position are held in extension `chrome.storage.session` under `kosmore.popup.{tabId}`. The background derives the tab ID from the top-frame Kosmora sender; content scripts cannot supply another tab ID. Pin/unpin/drag/resize messages are validated and serialized so page restoration reads state after preceding writes. Closing a tab removes its session entry. `Settings.popupPosition` also remembers the last pinned coordinates locally; width and height remain the existing settings fields. Drag and resize completion save automatically, including pointer cancellation. No card identity, account data, note text, or card details are persisted with the layout. Browser restarts reset session pinning, while local position and size remain available for the next pin.

Full page loads, reloads, history navigation, and same-document route changes restore a pinned empty shell. The shell displays only its header controls and centered `No Card Selected` message until hover/focus selects a card. Card requests from the previous page are aborted and their late results discarded. Pinning follows the current native modal parent when dialogs open or close. Unpinning restores the selected card's anchor placement, or dismisses an empty shell. Close and Escape clear pinning. Temporary viewport clamps preserve the preferred position and size. All eight resize edges/corners support pointer capture; the four edges also support arrow keys (10 pixels, or 50 with Shift). Settings pages update clean dimension fields after an automatic save while preserving dirty edits.

The Last Sold header uses the newest timestamp among returned completed sales for selected variants, independently of which tab is open. Amounts are integer millionths of Kosmo; two decimal places are computed with integer arithmetic and half-up rounding. The requested `$X.XX` label denotes Kosmo here; its tooltip identifies the finish, local sale date/time, and currency. Pending histories show Loading; empty successful histories show No sales; failures without a sale show Unavailable; incomplete/failed variant histories mark any displayed price partial. It does not make new game requests or describe the returned sample as the full market history.

## Navigation hotkeys

The five feature groups use accessible on/off switches at the right edge of their heading rows instead of separate enable-checkbox rows. These retain native checkbox keyboard behavior and the existing per-group save/cancel flow. Switching a group off immediately makes its settings read-only using a disabled fieldset, including dynamically rebuilt album buttons. A Disabled badge, dashed border, and dimmed content identify the disabled state. The enable switch and Save/Cancel buttons remain available; saving applies the feature change to open game tabs. Re-enabling restores editing without losing existing choices. Connected account remains a selection-only group.

The options page presents six independently anchored groups in order: Hover tooltip, Pinned albums, Tooltip stat boxes, Card overlays, Navigation hotkeys, and Connected account. One ordered list supplies both the content and navigation menu. Account discovery/selection is separate from the pinned-album catalog, pin ordering, and save/cancel controls. The pinned-album group identifies the selected account. A fixed left navigation jumps to each native hash anchor, marks the current group, and uses a compact icon rail on narrow screens.

`navigationHotkeysEnabled`, `cardOverlaysEnabled`, `statBoxesEnabled`, and `pinnedAlbumsEnabled` default to true, including when older settings omit them. Each group saves its own enable flag and preferences without clearing disabled configurations or overwriting another group's draft. Disabling navigation hotkeys stops shortcuts and cancels pending profile/alert navigation. Saved settings load before navigation handlers start. The card-overlays flag suppresses both card-corner and tooltip-header indicators and their signal checks. The stat-box flag hides the metric area and stops its auction-count request; enabled auction badges may still request their own count. The pinned-albums flag hides shortcut/add/remove controls while retaining an owned-copy chooser when the independent Sell action needs it. Re-enabling a group restores its saved choices and applies to already-open game tabs.

Public assets fetched from `/market` on 2026-11-04 confirm that Buy uses `/market`, Activity uses `tab=overview`, and the activity dashboard accepts `view=auctions` (My auctions) and `view=mine` (My activity). Evidence: `2f2dt6_k7hg9v.js`, dashboard `su` and page `sj`. Alerts is a native dialog opened by `button[data-testid="market-alerts"]` in the newer navigation layout or `button[data-testid="watch-open"]` in the earlier Buy layout. It has no direct page route. KosMore navigates to `/market#kosmore-alerts`, waits up to 15 seconds for either visible enabled button, removes its marker, and opens the existing dialog. This click opens preferences only; it does not save or change a watched word. On a Market page where the button is already available, the shortcut opens it directly.

The delivered shared navigation (`1bqd922175gcj.js`) links Pulsar to `/games`. Shell/profile links use `/u/{encoded handle}`. My Profile reads `/api/me` when invoked and discards delayed results after a later shortcut or URL change. Other shortcuts use the game's ordinary top-level page routes. Shortcuts are content-script key handlers limited to Kosmora tabs; no global browser command or additional permission is registered. Matching uses exact modifier flags and letter/number/F-key codes, and ignores form controls and editors through the event's composed path. `Settings.hotkeys` is local, starts empty for existing installations, and rejects corrupt or duplicate stored entries. The settings recorder reports duplicates before saving. Each settings group merges only its own draft keys into freshly read saved settings.

## Remaining live verification

Real album writes, server-side rejection details, full-art/shiny populated live sale responses, and populated opening payloads were not exercised under the read-only restriction. These paths are implemented from the delivered client and tested against synthetic contract fixtures. Do not describe fixture writes as successful real-game writes.
