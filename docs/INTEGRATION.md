# KosMore extension integrations

KosMore uses two connections. The extension service worker calls KosMore Services for shared market data and linked-player listings. The content script uses the signed-in Kosmora tab for game identity, owned copies, albums, and other player actions. The backend repository maintains its client contract in `KosMoreServices/resources/kosmore-services-api.md`. [Account setup](../README.md#connected-account)

## Connecting to KosMore Services

Enter the administrator's API base URL in **Connected Account**. HTTPS is required for remote hosts. Local development also accepts HTTP on `localhost` and `127.0.0.1` with an optional port. A deployment path prefix is supported. Connect and Copy Link request browser permission for the chosen host.

Since 2.0.1 the manifest supplies a stable unpacked extension ID. Register `chrome-extension://<extension-id>` as the extension origin and `https://<extension-id>.chromiumapp.org/kosmore-services` as the extension redirect URI in Services. Use the ID shown on the browser's Extensions page. Kosmora sends its provider callback to the backend's `/v1/connect/callback` route.

| Step | Extension request and response |
| --- | --- |
| Start | Generate a random 32-byte verifier and state, each encoded as unpadded base64url. `POST /v1/connect/start` sends `redirectUri`, `state`, `handoffChallenge` (the unpadded base64url SHA-256 digest of the encoded verifier), and optional `inviteCode`. Services returns a Kosmora `authorizationUrl` requesting the `identity`, `collection`, and `listings` scopes. |
| Approve | **Connect** opens the browser's identity window. **Copy Link** opens the same flow when the user pastes the URL in a tab in the same profile. A temporary redirect rule delivers the matching callback to the extension. The pending sign-in lasts ten minutes. |
| Exchange | The extension checks the redirect URI and state, then sends `code` and `handoffVerifier` to `POST /v1/connect/exchange`. The handoff code is valid for one minute. The response supplies `accessToken`, `expiresAtUtc`, and granted `scopes`. |
| Verify | `GET /v1/me` identifies the linked player. The worker stores the Services session in extension IndexedDB. Authenticated Services requests use a bearer token and omit cookies. |
| Disconnect | `POST /v1/disconnect` revokes the player's Services sessions and clears private cached data on the server. Confirmed listing history survives disconnect. |

When invite enforcement is enabled, approved players can reconnect without another code. An interrupted first sign-in may have already claimed the invite. `invite_unavailable` calls for a new code. A 401 or expired session calls for a new sign-in. A blocked player can use **Retry access** after reapproval. A missing listings scope disables private listing reads. [Connection and request handling](../src/services-background.ts)

## Card details and open listings

| Request | Data used by the extension |
| --- | --- |
| `POST /v1/cards/details` | Send up to 100 distinct positive decimal string card IDs in `ids`. Public reads set `includeMyListings` to false. A batch that also needs private listings can set both `includeMyListings` and `preferScopedBatch` to true. |
| `GET /v1/me/listings` | Read the linked player's open single-card auctions from `auctions`. The response's `X-KosMore-Fresh-Until` header controls snapshot expiry. Lots and face-down listings are omitted. |

Each entry in `cards` has its own `id` and `status`. A `fresh` or `stale` entry can carry `details`, `fetchedAtUtc`, and `freshUntilUtc`. `notFound` is an explicit, expiring negative result. `unavailable` leaves an existing cached value in place. A successful HTTP response can include mixed statuses and a `retryAfterSeconds` hint. The worker also respects `Retry-After` when requests are throttled.

`details.card` supplies the name, rarity, families, and quests. `details.auctions` supplies public prices and end times with a five-minute provider delay. `details.sales` and `details.history` supply per-finish summaries, latest sales, and daily figures for the 30-day history. Prices are digit strings in millionths of a Kosmo. Services uses `plain`, `shiny`, and `fullart`. The extension maps `shiny` to Kosmora's native `veil`. [Response parsing](../src/shared/services.ts)

The worker checks IndexedDB before batching misses and shares results across tabs. Visible demand can start a batch for one card. IDs already seen in a grid or game response can fill spare slots. Public records are keyed by Services base URL and card ID. The default local freshness limit is 300 seconds, bounded by the server expiry, with 30 days of retention for stale data. Refresh notifications update affected cards in open tabs. [Cache policy](../public/card-cache-config.json)

Private listings expire independently. The batch response supplies `myListingsStatus` and, when fresh, `myListingsFreshUntilUtc` at the top level. Each card row with private data carries its own `myListings` array. Other statuses are `not-requested`, `scope-missing`, and `unavailable`. The worker keys private rows by Services base and player ID, checks the signed-in game handle, and clears private snapshots when the connection changes. [IndexedDB store](../src/services-card-store.ts)

## Confirmed listing history

**My Last Listing** uses the original starting price from a confirmed submission. The browser captures successful game listings and queues confirmed records locally. It syncs for the matching player on connection, on startup, after capture, and about every five minutes while a Kosmora tab is open.

| Request | Contract |
| --- | --- |
| `GET /v1/me/listing-history/changes` | Read up to 200 records plus `generation`, `erasedAt`, `cursor`, and `hasMore`. Pass the generation and cursor (as `after`) to read the next page. |
| `POST /v1/me/listing-history/batch` | Send the current generation and 1–40 records containing auction `id`, `subjectId`, `startPrice`, `submittedAt`, and optional `copyId`. Success returns 204. A replay preserves the original record. |
| `DELETE /v1/me/listing-history?generation=…` | Erase the linked player's synced history and return the new generation and cutoff. Stale generations on writes or erasure return 409. |

Starting prices use micro-Kosmo strings. Submission times and erasure cutoffs use Unix milliseconds. On the next pull, the generation change and cutoff prevent an offline browser from uploading erased records again. The sync carries confirmed prices only. Notes, album pins, and settings move through the backup file. [Listing sync](../src/listing-history-sync.ts) · [Two-profile fixture](../tests/browser/listing-history.spec.ts)

## Native Kosmora requests

The following routes belong to Kosmora's game client. In particular, the price-history row describes a response the extension can observe while the game loads it. Shared market reads use the Services batch above. The native DOM and transport observations below were originally recorded in November 2026.

The delivered request wrapper prefixes paths with `/api`, sends `credentials: same-origin`, and accepts JSON. Mutations additionally send `Content-Type: application/json` and `x-kosmora: 1`. KosMore implements explicit album add and single-subject removal actions. It never retries a mutation automatically or invokes the native membership-toggle button.

| Request                                                         | Response used                                                                                                   | Evidence                                                                                                                  |
| --------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| `GET /api/me`                                                   | `handle`, nullable `currentOpening.id`                                                                          | Signed-in read; public request/session wrapper                                                                            |
| `GET /api/collection/{subjectId}`                               | `subjectId`, `name`, `rarity`, `interest.count`, `popularity.medianDailyViews`, `popularity.source`, `copies[]` | Signed-in read and card-detail client                                                                                     |
| `GET /api/cards/{subjectId}/prices?finish=plain\|veil\|fullart` | `{prices:{count,days,low,median,high,sales:[{auctionId,price,soldAt}]}}`                                        | Plain response read live; finish enumeration and schema checked in delivered CardSales module                             |
| `GET /api/albums`                                               | `{albums:[{id,name,items,...}]}`                                                                                | Native album list and picker code                                                                                         |
| `GET /api/albums?contains={subjectId}`                          | Album list plus `contains`, `containsCount`                                                                     | Signed-in read and picker code                                                                                            |
| `GET /api/openings/{openingId}`                                 | `id`, `state`, nullable `cards[]` with `slot`, `subjectId`, `instanceId`, `rarity`, `veil`, `card.fullArt`      | Read endpoint inspected in preparing state; populated schema and ordering established from delivered opening/recap client |
| `POST /api/albums/{albumId}/items`                              | Body `{subjectIds:[subjectId],copyId}`; response includes `added`                                               | Delivered native AlbumPicker add branch only; never exercised live                                                        |
| `DELETE /api/albums/{albumId}/items/{subjectId}`                | JSON body `{}`; membership absence is confirmed through the album list                                          | Delivered native AlbumPicker single-subject remove branch and JSON transport; never exercised live                        |

Market amounts are integer strings in millionths of a Kosmo (`100000000` displays as `100`). Count/price summaries cover the response window; transactions can be a smaller sample. A response window other than 30 days is rejected until the integration is updated. Wikipedia medians may be fractional and are not counts of interested players.

## Important semantics

- Album containment is queried at the subject level, even when a particular owned copy is selected for addition. If the album already contains the subject, KosMore does not replace its selected copy or invoke an add/delete toggle.
- The native picker has separate POST-add and DELETE-remove branches. KosMore uses a separate red trash action for removal and checks account identity and containment again immediately before either action. The album name itself never toggles membership.
- For addition, a copy must still appear in the current signed-in account's `/collection/{subjectId}` response immediately before the write. A copy ID in a market, social, or card URL does not prove ownership. Removal targets the verified subject-level membership and does not depend on which owned copy is selected.
- The native market finish selector uses `plain`, `veil`, and `fullart`. Copy flags preserve both `veil` and `fullArt`; visual recognition uses `.kc-veil`, `.kc-fa`, and reveal classes. Full art takes precedence in the native market finish classification.
- No dedicated fresh Wikipedia request is needed: the card detail already carries the recorded median and source.
- The delivered card-detail client links owned copies to `/market/sell?subject={subjectId}&instance={copyId}`. The footer Sell action uses this navigation only after fresh account/ownership checks and requires an available copy. It does not submit a market mutation.

## Pack identity and DOM mapping

The recap client flattens openings in the URL's order, sorts each opening's renderable cards by `slot`, and uses opening ID plus slot as the entry identity. The reveal client sorts standard before shiny before full-art, then ascending rarity and slot. KosMore reproduces this ordering only to obtain a candidate, then independently validates its subject and finish against the hovered DOM card and its exact instance against the owned-copy response.

Recap `.ko-grid > li` index, reveal `.ko-tray > li.on` count, and `.ko-viewer-count` provide the corresponding visible entry. Ambiguous or changed mappings fall back to an explicit owned-copy chooser.

Verified selectors:

- Ordinary cards: `.kc-link`, `.kc-article`, `/card/{id}` links, `/media/cards/{id}/...` image URLs, `[data-testid=card-corner]`.
- Reveal: `.ko-card.ko-beat-shown .ko-face-front .kc-article`; ignore backs and hidden faces.
- Recap: `.ko-summary .ko-grid > li` and `.ko-grid-open` overlay.
- Native enlarged preview: `.ko-viewer-sheet`, `.ko-viewer-count`.
- Market activity: visible `a.mk-act-main` within `.mk-act` (Your turn and Your bids under way), `a.md-lot-link` within `.md-lot` (Your cards on sale), and `.md-ledger > li > a` (the recent journal and expanded Day by Day journal). The visible auction link supplies the card context for thumbnails, names, summaries, and keyboard focus.

With **Use Overlay Button Instead of Hover** enabled, these compact activity surfaces receive one Kosmora button anchored to the bottom-left of the full `.mk-act`, `.md-lot`, or journal list row. The target shares its row's scrolling content, stays outside native auction links and bid/relist buttons, and preserves native layout. Hover and link focus do not open a tooltip while that row's button is showing; clicking or keyboard-activating the button opens its card through the existing popup path. Incremental scans follow replaced rows, hidden controls, and journal expansion/collapse. Turning the setting off removes the buttons and restores hover/focus. Compact thumbnails continue to omit price/signal overlays independently of tooltip buttons.

## Private social reminders

On Social, the reminder editor verifies the selected friend's collection and profile links before mounting the KosMore control. The inline editor and popup share the same account-scoped draft.

Reminders use one `chrome.storage.local` key per normalized account/friend handle (`kosmore.friend.{account}.{friend}`), independently of tooltip settings. `/api/me` is read to verify the account; notes and selected family names are never sent to Kosmora. Handle renames create a separate reminder entry, as with account-specific album pins.

Family choices come from the native `GET /api/atlas/families` catalog. The picker flattens domains and families and preserves saved names, including names the catalog no longer contains.

## Trade suggestions

Card families come from Services. Friend matches compare those family names with local reminders for handles in the verified account's native `GET /api/friends` response. Matches rank by matching-family count, then handle. The trade form's **Possible Interest** counts depend on complete, sendable collection results the game has already loaded for the relevant families.

## Trade notes

Trade reminders also show a filled Notes badge after the saved family badges when the verified account has nonblank notes for the selected player. It opens immediately on tap or after the configured hover/focus delay, and dismisses on Escape, outside click, or after leaving the badge and popup. Text is rendered literally, with line breaks, in a read-only view. Pinning moves the notes into a labeled block below the family badges and above Possible Interest; the header or Trade reminders settings can unpin it. Width, height, open/dismiss delays, visibility, and pin state use the existing settings save/cancel and backup paths. Player/account changes, navigation, reminder edits, and disabling the group dispose of the previous popup and timers. Notes remain available when no families are saved or family badges are hidden.

Family Impact is disabled on Fusion, Trade, Vortex, and Sell screens in this build. The legacy Fusion Next Batch helper has been removed.

## Sales price badges

The tooltip history tab merges locally saved listing rows with the matching player's open single-card listings. Refresh rereads the available cache. The Sell badge selects the latest confirmed starting price by submission time. A discount for a copy also needs local evidence of consecutive unsold listings.

The independent Sales Overlay group sits directly below Card overlays and applies to both Sell Several Cards (`/market/sell/batch`) and the single sell form (`/market/sell`). Turning the group off makes all its controls read-only and removes the functionality from open game tabs.

Each batch widget is inserted after its own price-control row. The single widget is inserted after the starting-price label, outside that label. Bid and reserve inputs and other routes are excluded. The single form's visual subject must match its URL while subject navigation settles.

The gold gavel and red sale tag badges share the card overlays' icons, colors, and price definitions across all finishes. A bounded concurrent visible-input queue uses the shared signal provider and client request scheduler; the card-overlay and hover-tooltip switches do not gate sales badges. While reads are pending, a neutral loading message appears. Each confirmed signal can render independently before slower lookups finish; last-sale prices remain unavailable until every finish has been checked. Completed-sale badges require a positive history signal, and red badges require confirmed active auctions; absent signals leave no badge or empty placeholder. If neither applies, the empty widget is hidden. A confirmed signal with unavailable pricing remains noninteractive. Authentication and rate-limit failures retain their status messages. The badge continues to display its original reference price. Up to six decimal places are supported. Nonpositive adjusted prices are rejected visibly and leave the field unchanged. These handlers change only the associated starting-price input and never submit the form, choose a copy, alter another card, or change a reserve. Native validation and fee/quote behavior still run as they do for a typed edit. Delayed results for removed, replaced, or navigated fields are discarded. Browser fixtures emulate controlled-input value tracking and cover both forms, positive/negative offsets, independent toggles, fixed fields, settings persistence, stale rows, and unchanged submission/copy controls. No real sale was submitted during verification.

## Private card notes and popup layout

The **Mobile Friendly** subgroup inside Hover tooltip contains **Use Overlay Button Instead of Hover**, **Outside Click Closes Tooltip Only**, and **Full Screen & Centered on Open**. All three default to false and save/cancel with the existing tooltip group. `fullScreenCenteredOnOpen` fills the visible viewport with a 24px margin on every side and centers immediately, without the opening animation. It adapts to window and visual-viewport resize/scroll events, including smaller visible areas while the keyboard is open. Saved width, height, and position are retained; their size controls and manual drag/resize are unavailable while this mode is enabled. Pinning still keeps the tooltip open and saves only pin state in this mode, preserving the previous size and position. Unpinned full-screen tooltips close from the outside margin; the independent outside-click-only preference controls whether that dismissal also consumes the underlying click. Friend tooltips retain their independent size settings.

The Hover tooltip setting **Outside Click Closes Tooltip Only** (`outsideClickClosesTooltipOnly`) defaults to false, including for older settings and backups. When enabled, an outside press dismisses an unpinned card tooltip and consumes the full pointer/mouse/touch activation, including the click after the tooltip disappears. Native card navigation, selection, and other underlying controls therefore wait for the next click. A new pointer press resets the guard, canceled gestures clear it, and completed presses expire if no click follows. Hovering a different card keeps the current tooltip visible until the next tooltip is ready, so a quick outside dismissal click is still intercepted. Actions inside the card tooltip or its friend companion remain available. Pinned tooltips and the default-off behavior keep their existing click-through behavior.

The Hover tooltip group includes the opt-in `useOverlayButtonInsteadOfHover` preference, labeled **Use Overlay Button Instead of Hover**. It defaults to false for new settings and older backups. When enabled, eligible visual cards show a circular button with the star-and-circle wordmark SVG copied from Kosmora's public page (`https://kosmora.io/`) and bundled in `src/content/kosmora-logo.svg`. Its center sits eight pixels inside the bottom-left corner. The 36px logo has a 44px touch target and extends slightly beyond the card. Each Shadow DOM target is positioned absolutely within its card's scrolling content, outside native links/buttons; scrolling carries it directly, without JavaScript scroll-position updates. Resize and page changes refresh local offsets, and clipping follows the native scroll container. On Sell Many (`/market/sell/batch`), the target attaches to the bottom-left of the whole `.bsell-row` listing box, keeping the small thumbnail clear. Tooltip presses do not select cards, advance packs, change copy/price controls, or submit sales. Hover/focus does not open or update a tooltip while the corresponding button is shown. A press uses the existing popup, account checks, copy resolution, and cached data, with no hover delay. Press-opened tooltips stay open for touch interaction until closed, dismissed outside, or navigated away; pinning remains available. The tooltip master disables the buttons independently of Card overlays. Other compact surfaces without a button retain normal hover behavior.

Albums marked Already added display a small red trash icon at the right edge of their tile. It is an independently focusable button beside the disabled album-name button, positioned within the same visual tile; no buttons are nested. Only the trash action removes membership. ## Backup and restore

The settings utility exports a versioned UTF-8 `kosmore-backup` JSON document with `formatVersion: 1`, `exportedAt`, `extensionVersion`, normalized `settings`, `marketFinishes`, `friendReminders` (`account`, `friend`, `value`), and `cardNotes` (`account`, `subjectId`, `value`). All saved accounts and reminders are included without querying current game sessions, friends, albums, or catalogs. Authentication, caches, unknown storage keys, and per-tab session layout are excluded. The file contains readable private notes; export reads persisted values rather than settings drafts. Existing supported note/settings schema versions remain independent of the backup format version.

Import validates the complete file before writes, including schemas, identifiers, settings ranges, duplicate record identities, shortcuts, note limits, and the 32 MiB file cap. The preview reports account/record counts and added, overwritten, removed, and unchanged entries. Preferences and market filters count as entries; each account pin list also counts separately. Merge uses imported preferences, replaces matching reminder/note records and pin lists, and retains destination-only records and account pin lists. Replace restores supported data and removes recognized destination records absent from the backup, while preserving unrelated keys. Empty notes intentionally clear existing text. Unknown backup envelope fields are never imported as storage keys.

Applying requires clean settings drafts; Replace additionally requires an explicit checkbox. The importer rechecks its preview against current supported data and checks the complete final storage footprint against the local quota, including unrelated keys. It snapshots affected keys, removes obsolete Replace records before the batch write to avoid temporary quota overflow, and attempts to restore the snapshot if either operation fails. A rollback failure is reported explicitly; this is not a storage transaction. The importing page reloads its saved/draft controls after success. Existing storage-change handlers update game tabs and preserve dirty note drafts. Browser fixtures verify file download, transfer to a fresh isolated profile without a game tab, Merge/Replace, cancellation, validation, keyboard/narrow layout, and open-tab updates. No live game-server writes are exercised by backup/import.

## Friend tooltip
