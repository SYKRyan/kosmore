# Kosmora integration evidence

Inspected 2026-11-04. This is an observed private web-client contract, not a stability guarantee or an official public API. Never log authentication headers or commit account inventories. Fixtures in `tests/fixtures` are synthetic.

## Transport

The delivered request wrapper prefixes paths with `/api`, sends `credentials: same-origin`, and accepts JSON. Mutations additionally send `Content-Type: application/json` and `x-kosmora: 1`. KosMore implements explicit album add and single-subject removal actions. It never retries a mutation automatically or invokes the native membership-toggle button.

| Request                                                         | Response used                                                                                                   | Evidence                                                                                                                  |
| --------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| `GET /api/me`                                                   | `handle`, nullable `currentOpening.id`                                                                          | Signed-in read; public request/session wrapper                                                                            |
| `GET /api/collection/{subjectId}`                               | `subjectId`, `name`, `rarity`, `interest.count`, `popularity.medianDailyViews`, `popularity.source`, `copies[]` | Signed-in read and card-detail client                                                                                     |
| `GET /api/cards/{subjectId}/prices?finish=plain\|veil\|fullart` | `{prices:{count,days,low,median,high,sales:[{auctionId,price,soldAt}]}}`                                        | Plain response read live; finish enumeration and schema checked in delivered CardSales module                             |
| `GET /api/albums`                                               | `{albums:[{id,name,items,...}]}`                                                                                | Native album list and picker code                                                                                         |
| `GET /api/albums?contains={subjectId}`                          | Album list plus `contains`, `containsCount`                                                                     | Signed-in read and picker code                                                                                            |
| `GET /api/openings/{openingId}`                                 | `id`, `state`, nullable `cards[]` with `slot`, `subjectId`, `instanceId`, `rarity`, `veil`, `card.fullArt`      | Read endpoint inspected in preparing state; populated schema and ordering established from delivered opening/recap client |
| `POST /api/albums/{albumId}/items`                              | Body `{subjectIds:[subjectId],copyId}`; response includes `added`                                               | Delivered native AlbumPicker add branch only; never exercised live                                                        |
| `DELETE /api/albums/{albumId}/items/{subjectId}`                | JSON body `{}`; membership absence is confirmed through the album list                                          | Delivered native AlbumPicker single-subject remove branch and JSON transport; never exercised live                        |

Market amounts are integer strings in millionths of a Kosmo (`100000000` displays as `100`). Count/price summaries cover the response window; transactions can be a smaller sample. A response window other than 30 days is rejected until the integration is updated. Wikipedia medians may be fractional and are not counts of interested players.

## Important semantics

- Album containment is queried at the subject level, even when a particular owned copy is selected for addition. If the album already contains the subject, KosMore does not replace its selected copy or invoke an add/delete toggle.
- The native picker has separate POST-add and DELETE-remove branches. KosMore uses a separate red trash action for removal and checks account identity and containment again immediately before either action. The album name itself never toggles membership.
- For addition, a copy must still appear in the current signed-in account's `/collection/{subjectId}` response immediately before the write. A copy ID in a market, social, or card URL does not prove ownership. Removal targets the verified subject-level membership and does not depend on which owned copy is selected.
- The native market finish selector uses `plain`, `veil`, and `fullart`. Copy flags preserve both `veil` and `fullArt`; visual recognition uses `.kc-veil`, `.kc-fa`, and reveal classes. Full art takes precedence in the native market finish classification.
- No dedicated fresh Wikipedia request is needed: the card detail already carries the recorded median and source.
- The delivered card-detail client links owned copies to `/market/sell?subject={subjectId}&instance={copyId}`. The footer Sell action uses this navigation only after fresh account/ownership checks and requires an available copy. It does not submit a market mutation.

## Pack identity and DOM mapping

The recap client flattens openings in the URL's order, sorts each opening's renderable cards by `slot`, and uses opening ID plus slot as the entry identity. The reveal client sorts standard before shiny before full-art, then ascending rarity and slot. KosMore reproduces this ordering only to obtain a candidate, then independently validates its subject and finish against the hovered DOM card and its exact instance against the owned-copy response.

Recap `.ko-grid > li` index, reveal `.ko-tray > li.on` count, and `.ko-viewer-count` provide the corresponding visible entry. Ambiguous or changed mappings fall back to an explicit owned-copy chooser. No private React props, fiber fields, hydration state, game local storage, or network interception hooks are used.

Verified selectors:

- Ordinary cards: `.kc-link`, `.kc-article`, `/card/{id}` links, `/media/cards/{id}/...` image URLs, `[data-testid=card-corner]`.
- Reveal: `.ko-card.ko-beat-shown .ko-face-front .kc-article`; ignore backs and hidden faces.
- Recap: `.ko-summary .ko-grid > li` and `.ko-grid-open` overlay.
- Native enlarged preview: `.ko-viewer-sheet`, `.ko-viewer-count`.
- Market activity: visible `a.mk-act-main` within `.mk-act` (Your turn and Your bids under way), and `a.md-lot-link` within `.md-lot` (Your cards on sale). The visible auction link anchors the popup for thumbnail, name, summary hover, and keyboard focus.

## Private social reminders

The public social client (`3i4rvn2i63msn.js`, with shared `Page` in `0e4alq37o-niu.js`) renders the selected friend as `section.sb-page[data-testid="sb-friend-card"]` inside `.sb-side`. KosMore mounts its own Shadow DOM panel immediately after that section, below the entire friend panel. Identity comes from matching `.sb-links` collection (`/friends/{handle}/collection`) and profile (`/u/{handle}`) links. A present `/social?f={handle}` must agree; a desktop default selection may have no `f` parameter. Other social subpages do not mount an editor. This uses delivered DOM contracts without inspecting React internals.

Reminders use one `chrome.storage.local` key per normalized account/friend handle (`kosmore.friend.{account}.{friend}`), independently of tooltip settings. `/api/me` is read to verify the account; notes and selected family names are never sent to Kosmora. Handle renames create a separate reminder entry, as with account-specific album pins.

New family tokens come from `GET /api/atlas/families`, the complete catalog used by `useFamilyChoices(true)` in the delivered card filters (`2ace7u1ogy3d9.js`, module `357445`). The response is `{domains:[{id,name,families:[{id,name,parent?}]}]}`; the picker uses `id`, `name`, and the domain's name. A signed-in read in the built-in browser verified 24 domains and 1,461 families on 2026-11-04; an unsigned request returned 401. There is no pagination in this catalog response. The adapter validates and flattens it, caching reads with the existing account-scoped five-minute cache. The editor accepts selected or exactly matched catalog names, supports punctuation such as commas within a family name, and preserves previously saved names that no longer match. Names remain the local reminder representation for compatibility with the initial editor. A failed catalog read disables new selections and offers Retry without blocking notes or removing stored tokens. No family preference is changed on the game's server.

## Trade suggestions

KosMore retains all listed memberships for matching; it does not infer other families from domain names or parent metadata. Missing or malformed family data disables suggestions without disabling market insights or album actions.

The social client's `useSocial` reads `GET /api/friends` and uses `friends[]` with each friend's `handle`. A signed-in read confirmed the top-level `friends`, `incoming`, `outgoing`, `blocked`, `limits`, `requests`, and `looks` fields; that account had no friends. The populated friend-entry shape comes from the delivered social client and synthetic fixtures. Suggestions use only this current friend list, not pending requests or reminder records for former friends.

The Trade tab loads its friend list on first use, verifies the account, and reads only `kosmore.friend.{account}.{friend}` keys for those friends. Matching compares saved family names with the card's actual membership names, ignoring case and whitespace. It does not use substring matching, hidden game interest data, or another account's reminders. Matches rank by matching-family count, then handle. Changes to local reminders invalidate an open popup's suggestions. Refresh/Retry explicitly refreshes the friend list. No trade is submitted; links open `/social?f={handle}`.

## Card overlays and quest membership

Card-corner overlays use the same DOM adapter as hover detection and consider only rendered visual cards. Text-only links, hidden faces, and decorative backs are excluded. A bounded concurrent queue checks visible cards; signal snapshots are cached per account and card for 30 seconds. Sale-history reads retain their five-minute cache; display-only ownership details use a separate 30-second cache; action checks always bypass it. Late results are discarded when the card identity or settings change. Badges use isolated Shadow DOM; passive badges pass pointer events through to the card, while the red market badge is a focusable link. Each indicator has a separate saved toggle and requires no hover.

The For Sale label appears at the top left with a black background and white text and border. History and the red gavel appear at the top right. Quest and friends share the bottom-right row, with quest immediately before friends when both are present. Narrow cards wrap the top-right badges without overlapping the For Sale label. That label requires an owned copy with a validated `auction_id` in the signed-in account's `/collection/{subjectId}` response; public auction counts, completed sales, and generic held/escrow states do not create it. This matches the native card-detail module's auction-link check (`33yu_fe2y9x88.js`, verified from the public asset on 2026-11-05). Any listed copy of the subject qualifies, across finishes. The default-on `showOnSaleOverlay` preference is independent of other indicators and the tooltip, and the card-overlay group switch disables it. The label does not appear in tooltip headers or on the compact thumbnails excluded below. Synthetic fixtures cover ownership, missing/invalid auction IDs, account reset, failure handling, widths down to 144px, pointer pass-through, and live settings changes.

The compact thumbnails within Market Activity's `.md-turn`, `.md-bids`, and `.md-sale` sections are excluded from overlay enumeration and from pending overlay results. They retain hover/focus detection, and the popup header still displays applicable indicators. Ordinary card overlays elsewhere remain controlled by their existing settings toggles.

The gavel badge requires a positive active-auction count for the exact subject across all finishes, using the same validated market search and 30-second count cache as the Active Auctions metric. A separate history badge requires a positive completed-sale count in at least one verified finish history within the 30-day response window. Either or both can appear; a past sale never creates an active-auction gavel. Their saved visibility settings are independent. Signal snapshots expire after 30 seconds, and card overlays use incremental visible-card discovery and a five-minute revalidation cycle. Existing hosts remain visible during routine same-account refreshes. An open popup gives its freshly loaded auction metric precedence over cached badge data, so Refresh can remove a gavel when auctions end. The friend badge uses the same current-friends and saved-family matching logic as Trade. Ordinary read failures suppress that signal; 401 pauses checks until session refresh and 429 respects the shared client cooldown.

On cards, history and the red gavel occupy the top right. Each badge can include a price to the right of its icon inside the same badge. The history price is the newest returned sale across every finish in the 30-day histories. A failed finish read hides the price while preserving any confirmed history icon. The gavel price is the lowest current listing price among exact-subject, open, unexpired auctions across all pages and finishes. Each listing uses `bestBid ?? startPrice`, matching the native market's `priceNow` and price sorting (`07dupywtiuf2v.js`, rechecked from the public asset on 2026-11-05). Prices are compared using integer micro-Kosmo; unavailable pricing on any qualifying listing hides the minimum without losing the count. The count and lowest-price client methods share one account-scoped 30-second summary cache and paginated search. Prices use the tooltip's dollar prefix for Kosmo amounts. Oversized amounts truncate visually while retaining their full accessible description.

The default-on `showLastSalePriceOverlay` and `showLowestListingPriceOverlay` switches sit beneath their respective icon preferences, with explanatory help text. A disabled parent makes its price switch read-only without clearing the saved choice; the card-overlay master disables all of them. Disabling a price preserves its icon. Hiding the history price permits early exit after a confirmed sale; hiding the listing price skips its lookup. Tooltip header indicators retain their compact icon layout. Synthetic tests verify the two rows, icon order, red styling, prices across finishes and pages, shared reads, failure isolation, default/save/cancel behavior, and 144px card layouts.

`GET /api/quests` was verified through a signed-in built-in-browser read and the delivered quest hook (module `925729`, including `0qlrvpfh1jxkd.js` and `2ace7u1ogy3d9.js`). It returns `{quests:[{id,state,stars:[{subjectId,lit,...}],...}],following,max,cards}` without pagination. The inspected response and native quest catalog listed 30 quests of 15 stars each. KosMore extracts and deduplicates only validated subject IDs from every quest's stars. It does not store account progress, interpret `held` as membership, or require a quest to be followed. Lit stars remain members. The native `/quests/wanted` contract is intentionally narrower (followed quests still needing cards), so it is not used for this badge. No follow, drop, celebration, or quest mutation is called. Missing, locked, or unfamiliar catalogs produce no quest badge; sales and friend badges can still load. Synthetic fixtures preserve this response shape without account inventory or progress dumps.

## Extension performance

All response caches are bounded in-memory caches scoped to the game tab and account; no backing database or persisted response store is required. A shared scheduler permits at most three simultaneous API reads, limits background reads to two to reserve capacity for interactions, prioritizes queued hover/click work, and checks the shared 429 cooldown before sending queued reads. Both overlay queues process up to two visible entries concurrently without the former 400 ms per-entry delay. Independent signals load concurrently and publish confirmed partial results; icons do not imply that a pending price is known.

Display-only account reads are deduplicated and cached for two seconds. Account checks for actions, private reminder loading, and focus/session revalidation stay fresh. Other caches are separated: card details and openings expire after 30 seconds, price histories and catalogs after five minutes, album display data after 10 seconds, and auction summaries after 30 seconds. Album actions verify fresh membership and invalidate only album data rather than discarding unrelated histories. Account changes and 401 responses clear private caches and old views; late responses from a previous account are rejected. Canceling one consumer never cancels a shared request while another consumer still needs it.

The main page features share one mutation observer and one frame batch, discover cards and sales inputs in changed subtrees, and validate individual sales rows directly. Overlay insertions do not schedule another page scan. Popup history renders are grouped by animation frame and retain the finish-filter controls. Album reads are deferred until pinned albums need them, including when pins are enabled in an already open popup.

`pnpm test:browser --grep performance:` runs synthetic regressions for concurrent 20-card loading, no full collection scan on an unrelated text update, repeat-hover request reuse, deferred album loading, progressive quest badges, and host retention during focus refresh. Its timing output is a local fixture measurement, not a live Kosmora latency claim.

## Backup and restore

The settings utility exports a versioned UTF-8 `kosmore-backup` JSON document with `formatVersion: 1`, `exportedAt`, `extensionVersion`, normalized `settings`, `marketFinishes`, `friendReminders` (`account`, `friend`, `value`), and `cardNotes` (`account`, `subjectId`, `value`). All saved accounts and reminders are included without querying current game sessions, friends, albums, or catalogs. Authentication, caches, unknown storage keys, and per-tab session layout are excluded. The file contains readable private notes; export reads persisted values rather than settings drafts. Existing supported note/settings schema versions remain independent of the backup format version.

Import validates the complete file before writes, including schemas, identifiers, settings ranges, duplicate record identities, shortcuts, note limits, and the 32 MiB file cap. The preview reports account/record counts and added, overwritten, removed, and unchanged entries. Preferences and market filters count as entries; each account pin list also counts separately. Merge uses imported preferences, replaces matching reminder/note records and pin lists, and retains destination-only records and account pin lists. Replace restores supported data and removes recognized destination records absent from the backup, while preserving unrelated keys. Empty notes intentionally clear existing text. Unknown backup envelope fields are never imported as storage keys.

Applying requires clean settings drafts; Replace additionally requires an explicit checkbox. The importer rechecks its preview against current supported data and checks the complete final storage footprint against the local quota, including unrelated keys. It snapshots affected keys, removes obsolete Replace records before the batch write to avoid temporary quota overflow, and attempts to restore the snapshot if either operation fails. A rollback failure is reported explicitly; this is not a storage transaction. The importing page reloads its saved/draft controls after success. Existing storage-change handlers update game tabs and preserve dirty note drafts. Browser fixtures verify file download, transfer to a fresh isolated profile without a game tab, Merge/Replace, cancellation, validation, keyboard/narrow layout, and open-tab updates. No live game-server writes are exercised by backup/import.
